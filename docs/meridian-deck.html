Meridian

A non-custodial dApp for trading Yes / No tokens on whether a MAG7 stock closes at or above a strike — today.

Each contract pays $1.00 USDC to the winning side.   Yes + No = $1.00, always.

Architecture review · PEAK6 Stack · Rust / Anchor · Next.js · Pyth Target · Solana devnet
The Product 02 / 12
One question, settled daily

“Will [STOCK] close at or above [STRIKE] today?”

A same-day (0DTE) binary options market. Deposit $1.00 to mint a Yes+No pair, trade either leg on an on-chain order book, and redeem the winning side after the 4:00 PM ET close.

01 · MINT

Deposit collateral

Lock $1.00 USDC into a program vault → receive 1 Yes + 1 No token.

$1 in ⇒ one complete pair out
02 · TRADE

One book, four actions

Buy/Sell Yes or No on a single on-chain CLOB. Yes price = market-implied probability.

Yes @ $0.65 ⇒ No is implicitly $0.35
03 · SETTLE

Oracle decides

At close, an on-chain price oracle writes the outcome. Winners redeem $1.00 each; losers, $0.

close ≥ strike ⇒ Yes wins, else No
Design north star

Non-custodial by construction. No human or service ever holds user funds — correctness is enforced by code and math, not by trusting an operator.

Trust Boundaries 04 / 12
Where trust lives — and where it doesn't

Trust is concentrated on-chain, by design.

TRUST ROOT

The Program

The only thing that can move funds. Mints, vault, matching and settlement all validated here. PDAs mean no private key controls the vault or the mint authority.

enforces all six invariants
CONVENIENCE

Automation Service

Holds a keypair that can call permissioned create/settle instructions. It cannot violate invariants or drain the vault.

a liveness convenience — not a trust root
ZERO TRUST

The Frontend

Holds nothing. The user's wallet signs every state-changing action. It only translates intent and renders state.

custody = 0
The mechanism

The vault & mint authority are PDAs — addresses derived from the program with no private key. Funds and token issuance are controlled only by program logic. This is what makes “non-custodial” true rather than marketing.

The Order Book 05 / 12
The single most important design concept

One book. Four actions. Two perspectives.

Each strike has exactly one order book: Yes traded against USDC. Because Yes + No = $1.00, selling a Yes is economically identical to buying a No.

Buying Yes · same side
Buy YesLift the ask side directly.
Sell NoBuy a Yes → now hold Yes+No = redeemable $1.00, closing the No exposure.
Selling Yes · same side
Buy NoMint a pair, sell the Yes on the bid, keep the No. Cost = $1.00 − Yes sale.
Sell YesPost on the ask / hit a bid.
price of Yes (0.00 – 1.00) = market-implied probability the stock closes at/above the strike

→ The frontend flips perspective; under the hood it is always a single Yes/USDC book. This collapses four UI buttons into one matching engine — and keeps trade, mint and redeem state cohesive in one program.

Transaction Flow 06 / 12
A contract's life · mint → trade → settle → redeem

How a transaction processes, end to end.

Every value-moving step is either a user-signed transaction or a program-enforced rule. The settlement crank is idempotent and, where possible, permissionless — so markets can settle even if our service is down.

Tradeoff · ADR-002 08 / 12
Build vs integrate the matching engine

We built a minimal on-chain CLOB.

Meridian needs many short-lived markets created and retired daily — a poor fit for Phoenix's long-lived-spot model. Our instruments are also simpler: price is bounded $0–$1, one book per strike.

Build minimal CLOB

Chosen
WinTrustless + fully on-chain; mint/redeem invariants wired directly into trading; no cross-program glue.
CostMatching is perf-sensitive & edge-case heavy. Mitigated by scoping to “minimal” + a cap N per side.

Integrate Phoenix

Rejected
WinBattle-tested engine, no matching code to audit.
CostBuilt for long-lived spot pairs; uncertain per-market setup cost on devnet; external dependency that can dead-end.

Per-order accounts
+ off-chain matcher

Rejected
WinSimplest on-chain footprint.
CostReintroduces a trusted matcher — breaks the “transparent & auditable” pitch.
The accepted trade-off

A cap N on resting orders per side. A documented demo limitation; the production path is a Serum/Phoenix-style slab.

Tradeoff · ADR-004 09 / 12
The highest-risk dependency in the system

Pyth — behind an interface, with a fallback.

Settlement is purely numeric (“is AAPL ≥ $215?”), so a deterministic price oracle beats a human/optimistic one — no dispute window. Pyth publishes native confidence intervals and is the main on-chain source of real-time US equities.

Why Pyth

Chosen
FitNative confidence bands map directly onto the brief's confidence check.
ProofPowers Polymarket's equity markets — production validation.
DevnetPull oracle: we post the Hermes update via the Receiver (same program ID on devnet & mainnet) — so we can likely get equity prices onto devnet ourselves.

The risks we accept

Watch
HoursEquity feeds only update during US market hours; 4:00 PM ET sits at the session boundary — automation must encode the market calendar.
ClusterFeed IDs differ per cluster — must use the devnet ID, looked up live.
Overrideadmin_settle is a centralization point — bounded by enforced time delay, admin-only, fallback-only.
Open question · resolve first

Do all 7 MAG7 feeds return a fresh price on devnet during market hours? Verified live before settlement code ships — fallbacks ready: crypto-feed stand-ins, a mocked oracle, or mainnet-beta with tiny amounts.

Correctness 10 / 12
Guarantees enforced on-chain · proven for all prices

Six invariants. The whole safety case.

01
Collateralization — the vault always backs every outstanding pair, exactly.
vault_USDC == $1.00 × pairs_minted · any fee goes to a separate account, never the vault
02
Payout completeness — the two sides always sum to a dollar.
Yes_payout + No_payout == $1.00 at settlement, always
03
Token provenance — tokens are created only by mint_pair and destroyed only by redeem.
program holds mint + freeze authority via PDA
04
Settlement immutability — once outcome & price are written, they cannot change.
05
Settlement timing — settle_market rejects before 4:00 PM ET; admin_settle rejects before its enforced delay.
06
Oracle quality — settlement rejects stale prices and prices whose confidence band exceeds the configured threshold.
Risks & Delivery 11 / 12
Honest about limitations · sequenced to de-risk

What could break — and how we build around it.

⚠ Highest risk

Equity feeds on devnet

Pyth equity feeds update only during US market hours; feed IDs differ per cluster.

Mitigation: live devnet spike first; crypto stand-ins / mock / mainnet fallback.
Demo-grade

Order book scope

Bounded-array book caps resting orders per side; not high-throughput.

Mitigation: production path is the slab model.
Liveness

Automation SPOF

A single scheduler is a single point of failure — for timing, not funds.

Mitigation: idempotent + permissionless settle; retries + alerts.
Centralization

Admin override

admin_settle is a trusted fallback path.

Mitigation: time delay + admin-only + use-on-failure only.
Delivery strategy · critical-path-first

scaffold → mint/redeem → settlement + oracle spike → shared TS SDK → frontend → integration → one-command devnet deploy

Order-book & market-creation tracks run in parallel after scaffold; automation + frontend fan out after the SDK. The #1 risk is de-risked inside the settlement feature before any settlement logic is committed.
